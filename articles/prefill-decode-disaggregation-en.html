Prefill–Decode Disaggregation: Resource Configuration, KV Handoff, and Cache Reuse

From Splitwise, DistServe, and Mooncake, explore how phase-specific resources, KV handoff, and shared caching shape LLM serving.

Published August 25, 2025 Updated September 28, 2026

Scheduling and resource management in LLM inference systems. Drawing on Splitwise, DistServe, and Mooncake, this article discusses the configuration options created by phase disaggregation, as well as the costs of state transfer, cache reuse, and request routing. Recommended prerequisite reading: LLM Inference Scheduling: How to Balance Throughput and Response Latency

Chunked Prefill can limit the impact of a long input on a single iteration. However, as long as Prefill and Decode still run on the same instance, the two phases must share hardware, GPU memory, and one model parallelism configuration. Yet they favor different configurations, making it hard to meet both requirements by adjusting execution order alone. Prefill–Decode disaggregation therefore takes the problem one step further: configuring execution resources for the two phases separately. [1][2][3]

Independent configuration also adds a data-transfer path that must be completed. The KV cache produced by Prefill must be handed to another set of execution resources to continue Decode. Once these states can also be reused across requests, where the cache resides and whether it is worth moving will, in turn, change where requests should be sent. [4]

To understand P/D disaggregation, we will follow the causal chain of “decoupling execution resources → resource ratios and placement → KV handoff → cache reuse and routing.” Splitwise, DistServe, and Mooncake provide representative designs and evidence for these questions. We will use these questions to organize the comparison and determine under what conditions the benefits of disaggregation can cover its added costs.

1. Phase Disaggregation: Configuring Resources Independently for Two Types of Computation

1.1 Why Colocated Deployment Constrains the Configuration of Both Phases

An autoregressive request first goes through Prefill to process its input and build the KV cache, then through Decode to keep generating subsequent tokens. Prefill can process multiple input positions at once, while small-batch Decode is usually more constrained by memory access. The two phases therefore differ in their needs for batching, compute capacity, memory bandwidth, and state capacity. Through model measurements and analysis of production request traces, Splitwise examines how these differences affect power consumption, cost, and cluster design.[1]

When the power cap drops from 700 W to 350 W, the Decode generation interval in the right-hand figure barely changes, while the Prefill first-token latency in the left-hand figure has already increased. When the cap is reduced further to 200 W, Decode latency also rises noticeably. This shows that the two phases differ in their sensitivity to the power budget and provides a measurement basis for setting separate power caps.[1]

Colocated deployment must coordinate these needs within the same instance. After disaggregation, the number of instances used by Prefill and Decode, how the model is partitioned on each instance, and the batch size for each iteration can all be decided separately. Hardware types can also be chosen independently.[1][2]

Note: Here, an “instance” means a model-serving unit capable of executing the corresponding phase; it may itself span multiple GPUs. A request is first sent to a Prefill instance, after which its KV state is handed to a Decode instance to continue generation.[2]

1.2 Splitwise: How Resource Pools and Two-Level Scheduling Work Together

Splitwise organizes machines into three resource pools: the Prompt Pool handles Prefill, the Token Pool handles Decode, and machines in the Mixed Pool handle both types of work. All machines preload the model; the resource pool determines which phase of computation they currently handle. The cluster-level scheduler (CLS) manages these pools and assigns requests, while the machine-level scheduler (MLS) organizes actual execution on each machine.[1]

Following the Prompt Pool, KV transfer, and Token Pool, the normal phase-disaggregation process can be divided into three steps:

  1. Select machines for both phases at the same time: After a request arrives, the CLS measures queue lengths by the number of tokens awaiting processing and selects a Prompt machine and a Token machine with shorter queues. Both machines are determined at this point, so the subsequent KV transfer has a destination.
  2. Process the input on the Prompt machine: This machine executes Prefill, produces the first output token and the corresponding KV cache, and transfers the KV state to the selected Token machine. An InfiniBand connection carries this data path.
  3. Continue generation on the Token machine: Using the received KV, the Token machine generates subsequent tokens step by step until the request ends. It uses continuous batching to organize current generation requests in each iteration.[1]

Selecting the Token machine in advance also allows the KV for a longer input to be sent layer by layer during Prefill, overlapping transfer with computation in later layers. The CLS selects execution destinations. After a request enters a local queue, the MLS decides in which iteration and with which other requests it will run. The MLS continuously tracks the queue and GPU memory and periodically reports their state to the CLS for subsequent routing. The three types of machines use different batching strategies:[1]

Machine typeMLS execution strategy
Prompt machineProcesses inputs in first-come, first-served order and limits the total number of input tokens in a combined batch.
Token machineAdmits generation work in first-come, first-served order and expands the Decode batch as much as GPU memory allows.
Mixed machineExecutes both phases together and prioritizes new inputs to meet TTFT requirements. When resources are insufficient, it can preempt Decode while raising the priority of generation requests that have waited longer and limiting the number of times each request can be preempted, so that generation requests do not go without execution for a long time.

The Mixed Pool helps alleviate resource imbalances in serving. For example, when the Token Pool's queue exceeds a threshold, the CLS first tries to assign generation work to the Mixed Pool. If that pool also lacks capacity, it brings in a machine from the Prompt Pool, letting it temporarily handle Decode and enter a mixed execution state. Likewise, when Prefill pressure is too high, a Token machine can be borrowed in the opposite direction.[1]

A machine entering the Mixed Pool retains its original resource-pool identity. After finishing the temporary work from the other phase, it returns to its original pool. Only if the load deviates from initial expectations for a sustained period does Splitwise redefine the machines' phase roles at a lower frequency. These correspond to short-term borrowing and long-term adjustment of resource ratios, respectively. This dynamic adjustment can ease the situation in which one side has a queue while the other has spare capacity. How many machines Prefill and Decode each need, and what hardware to choose, depends on the requests' input and output characteristics and the latency and cost objectives the service must meet.[1]

2. Resource Configuration: Finding Effective Capacity Under SLO Constraints

2.1 Input and Output Lengths Alone Cannot Determine Resource Ratios

Long inputs mainly increase Prefill's computational burden, while sustained generation depends more on Decode serving capacity and KV capacity. Resource ratios need to account for the distributions of input and output lengths, the request arrival rate, and the execution cost, batching efficiency, and cache-hit behavior on the target model and hardware. The effects of long-tail requests on latency and KV occupancy should also be considered; machines cannot be allocated solely by the average token count.[1][2][4]

This also limits simple judgments about hardware. Higher peak compute, more GPU memory, greater bandwidth, and lower price each address a different bottleneck. Splitwise compares homogeneous, heterogeneous, and power-constrained configurations, producing design choices for particular workloads and constraints.[1] Comparing these configurations therefore also requires a common measure of service performance: with a given resource budget, how much request load can the system handle while meeting the requirements for first-token latency and subsequent generation intervals?[2]

2.2 Goodput: Measuring Serving Capacity Under Latency Targets

More resources and larger batches may increase throughput, but queueing may also cause many requests to exceed latency requirements. DistServe therefore optimizes for goodput: given TTFT and TPOT targets and a required SLO attainment rate, it seeks the request arrival rate the system can support per GPU.[2] For example, suppose that with the same GPU budget, configuration A completes 100 requests per second, but only 70% meet the agreed latency. Configuration B completes 90 per second, with 95% meeting the target. If the requirement is a 90% attainment rate, B can meet the service objective. A has higher throughput but fails to meet the latency requirement.

The resource-configuration objective is thus clear: under a fixed cost or GPU budget, maximize serving capacity that meets the latency constraints. How fast each phase runs on its own is only an intermediate measure; ultimately, we need to see whether the two phases together can stably process the same request stream.[2]

2.3 Parallelism Plans and Node Placement Must Be Decided Together

Phase disaggregation allows model parallelism to be chosen separately for Prefill and Decode. Tensor parallelism (TP) partitions computation within a layer; it may shorten a forward pass while introducing communication between devices. Pipeline parallelism (PP) partitions execution stages by layer and needs a steady supply of work to reduce idle time. Multiple complete model replicas provide serving concurrency. PP assigns different layers to different devices, while TP lets multiple devices compute the same layer together. They can be combined: first partition layers into pipeline stages, then apply TP within each stage.

The parallelism plan also determines between which GPUs KV must be transferred. DistServe therefore plans how to partition the model and where to deploy each part while configuring resources for the two phases. When cross-node bandwidth is low, it uses PP to divide the models for both phases at the same layer boundaries, then places corresponding layer segments on different GPUs within the same node. The KV produced by each Prefill segment can then be passed to the corresponding Decode segment over a high-speed intra-node connection, reducing waiting caused by cross-node transfer.[2]

The Controller first assigns a request to a Prefill instance to process its input, then passes it to a Decode instance to continue generation. The two types of instance are connected through KV cache transfer. Each instance holds a complete copy of the model, while its internal Parallel Runtime executes the model across multiple GPUs. The placement optimization described above further determines which nodes host these GPUs: placing the corresponding layer segments of the two phases on different GPUs in the same node lets the KV handoff use intra-node connections.[2]

This also shows that P/D disaggregation does not depend on heterogeneous hardware. Its focus is how independently configuring the phases and arranging communication can improve capacity under SLOs within the same resource budget, rather than explaining all gains by changing GPU models.[2] Whatever plan is used, Prefill and Decode still depend on the same request state. To determine whether this placement pays off, we also need to account for the KV data path that connects the two phases.

3. KV Handoff: How Transfer Costs Enter Request Latency

3.1 Estimating KV Transfer Volume with a Specific Model

For a standard KV cache with the same structure at every layer and a complete history retained, let the number of layers be L, the number and dimension of KV heads at each layer be H_KV and d, the number of cached tokens be S, and the number of bytes per element be b. Taking OPT-6.7B as an example, use the 2,048 maximum positions in its configuration as the number of cached tokens and assume that KV uses FP16 (excluding costs such as block metadata, padding, and extra copies):

M_KV ≈ 2 (Key and Value) × L × H_KV × d × S × b
     = 2 × 32 × 32 × 128 × 2,048 × 2 bytes
     = 1,073,741,824 bytes = 1 GiB

If the corresponding layer segments for Prefill and Decode are on different nodes, the KV handoff is constrained by the network link. Taking one 100 Gb/s port on an Intel E810-CQDA2 Ethernet adapter as an example, its nominal line rate converts to 12.5 GB/s, giving a lower bound of approximately:

T_payload,min ≈ KV data volume / port line rate
              = 1,073,741,824 bytes / 12,500,000,000 bytes/second
              ≈ 0.086 seconds ≈ 86 milliseconds

Protocol overhead, queueing, memory copies, and layout conversion all increase the actual time required. If transfer overlaps with Prefill, the wait visible to the user may be shorter than the full transfer time.[1]

3.2 How Layerwise Transfer Shortens Handoff Waiting

The most direct way to hand off the KV cache is to wait until all Prefill computation has finished, then send the KV, with Decode starting after receipt is complete (computation and transfer occur sequentially). Splitwise further uses asynchronous layerwise transfer: once a layer's KV has been produced, it begins sending it while computation continues on later layers.[1]

This reduces the transfer tail that remains on the critical path after Prefill finishes. Overlap does not eliminate the KV bytes; the network, memory copies, and synchronization still consume resources. Input size, compute time, and link capacity together determine how much of the transfer can be covered, while fine-grained handoff also incurs synchronization overhead. Splitwise therefore uses different transfer methods for different input sizes.[1]

3.3 When the First Token Is Returned Changes Where the Latency Falls

In a common execution pattern, Prefill can already produce the first output token. If the system returns it immediately from the Prefill side, the subsequent KV handoff may appear as a long gap between the first and second tokens. If the system waits until the state handoff is complete before returning the first token, the same wait may instead count toward TTFT. Splitwise's discussion of serial handoff addresses precisely this dependency after the first token and before the next generation step.[1]

Measurements therefore need to record both how long the data transfer took and how much longer the user waited. The former describes the data path; the latter also depends on overlap, queueing, and the response policy. Even if the transfer for one request is fully covered, the network may still become saturated as concurrency increases and become a source of visible latency again.[2]

So far, KV has been the state handed between two phases of the same request. If it can be reused by other requests, the question expands from “how to transfer it faster” to “which computation is worth avoiding, and where to obtain the state to do so.”

4. Cache Reuse: How KV Location Affects Request Routing

4.1 Mooncake: From Prefix Hits to Instance Selection

Multi-turn conversations, shared system prompts, and repeated questions about the same document may contain the same input prefix. If the model and execution conditions are compatible, the KV for this prefix can be reused to reduce repeated Prefill. Mooncake organizes reusable KV as a distributed storage resource and has its Conductor consider prefix hits, data location, and execution load together when scheduling. This adds a shared-state management layer between the Prefill and Decode pools. [4]

Note: Whether two requests can share KV depends on whether they have the same token sequence from the beginning. Content that is semantically similar but differs in tokens must still be computed again.[4]

The Conductor first selects Prefill and Decode instances. When selecting Prefill, it compares prefix hits at different locations, the transfer needed to retrieve the cache, and queueing time. When selecting Decode, it also checks whether the generation load can meet the TBT requirement. Mooncake Store is a KV cache pool distributed across resources such as DRAM and SSD on different nodes, and the Transfer Engine moves cache blocks over the network.[4]

  1. Read an existing prefix: If the KV for an identical token prefix is already in the cache pool, the selected Prefill instance retrieves it to the GPU. If there is no hit, this step is skipped.
  2. Compute the new input: Prefill computes only the subsequent tokens that did not hit the cache. A longer input can be processed in chunks, and the newly produced KV is written to the cache pool.
  3. Hand off this request's state: As Prefill produces KV layer by layer, the Transfer Engine asynchronously sends it to the memory of the Decode node selected in advance. Transfer can overlap with subsequent Prefill computation. The destination ultimately needs to receive all the KV required to continue generating this request.
  4. Continue generation: After loading the KV onto the GPU, the Decode node adds the request to a continuous batch and generates output token by token.[4]

Step 1 reuses a shared prefix left by earlier requests to avoid repeated Prefill. Step 3 hands off the current request's generation state so that another instance can continue Decode. The constraints on these two kinds of state therefore also differ: Prefill seeks to reuse as much cache as possible under TTFT and compute-utilization requirements, while Decode organizes generation batches under TBT and GPU-memory-capacity constraints.[4]

4.2 Why the Shortest Queue May Not Finish First

An idle node may have to compute a long input from scratch, while another node, despite having a queue, may already have most of the prefix cached. A third node may have to retrieve the state remotely. Comparing destinations therefore requires considering at least the wait, the computation for the uncached portion, and the additional retrieval.

The following hypothetical numbers illustrate this decision (for ease of comparison, temporarily treat the three costs as non-overlapping and assume all other costs are equal):

Candidate locationQueueingComputation for uncached portionAdditional cache retrievalEstimated completion time
A: idle, no usable prefix0 ms120 ms0 ms120 ms
B: local prefix, longer queue45 ms20 ms0 ms65 ms
C: retrieve prefix remotely5 ms20 ms55 ms80 ms

Under these assumptions, B finishes first despite having a longer queue. If B's queueing increases by another 100 ms, the choice changes. Queue length, cache-hit rate, and transfer distance each describe only part of the cost; what routing really needs to estimate is the request's completion time after arriving at that location. Mooncake's cache-aware scheduling combines input length, prefix matches, and load to estimate execution cost while also addressing hotspots introduced by the shared cache. Keeping only one copy of a popular prefix may concentrate many accesses on one node. Adding replicas spreads accesses but uses more capacity. Mooncake also uses early rejection in admission control to prevent requests predicted to miss their SLOs from worsening overload.[4]

This reconnects caching strategy with resource ratios: more hits may reduce Prefill compute demand, but replication, remote reads, and state handoff consume memory and network capacity. The value of a shared cache must be judged along the entire path.[4]

4.3 How Much Computation Does a Global Cache Actually Save?

Mooncake's cache ablation study provides a concrete observation. It uses 10 Prefill nodes, each with cache capacity for 3 million tokens, and limits each request's output to 1 token to isolate the effects of subsequent Decode. Local Cache can access only the cache on its own node, while Global Cache can share across nodes and migrate states proactively. The local-cache comparison also preferentially routes requests to nodes with more prefix matches.[4]

On the Synthetic workload, the global cache's hit rate is approximately 2.36 times that of the local cache, and Prefill GPU time falls to approximately 0.52 times the local-cache value. This shows that with that capacity, node count, and request distribution, a larger accessible cache range does reduce repeated computation. The work also separately reports experience from Kimi's production deployment and experiments using a dummy model with the LLaMA3-70B architecture and replayed workloads.[4]

5. Scheduling Phase Resources and KV State Together

Splitwise, DistServe, and Mooncake emphasize different decisions, and their experimental hardware, models, workloads, and SLOs are not entirely the same. In comparing them, we identify which cost each changes and what conditions limit that change.

WorkCore decision examined hereMain opportunity usedCosts that the benefit must cover
Splitwise[1]Resource pools and hardware configurations matched to each phaseThe two phases differ in their needs for compute, bandwidth, capacity, and powerResource-pool imbalance and KV handoff
DistServe[2]Resources, parallelism plans, and instance placement under SLOsIndependent configuration of the phases can increase effective serving capacity per GPUCommunication constraints, queueing, and resource investment
Mooncake[4]Global KV reuse and cache-aware routingRepeated prefixes across requests can reduce Prefill computationCache capacity, remote access, hotspots, and prediction errors

These approaches can be combined. Chunked Prefill changes how much work is executed in each iteration, P/D disaggregation changes which resources execute the work, and prefix caching reduces the input work that actually needs to be done. Chunked scheduling remains present in Mooncake's Prefill pool in Figure 7, a concrete example of such a combination.[3][4]

Viewed together, the three works expand the object of optimization from the execution efficiency of each phase to the entire path of resources and states traversed by a request. Independent configuration lets each phase use suitable resources, but also places KV handoff on the critical path. Shared caching reduces repeated computation, while making the location of state affect request routing. Each additional scheduling option introduces another constraint to coordinate.[1][2][4]

Whether disaggregation is worthwhile therefore depends on whether the added configuration options outweigh the costs of KV movement and resource-pool imbalance. Speeding up Prefill or Decode alone may not improve the wait over the whole request. A higher cache-hit rate does not mean that retrieving KV remotely is necessarily cheaper than recomputing it. Convincing results show how many arriving requests the system can bring within the target under the same resource budget, request trace, and latency objectives, and how many requests it rejects.[2][4]

Input and output lengths, arrival intensity, and the amount of shared prefix all shift the system's bottleneck. Splitwise uses the Mixed Pool to respond to changes in phase pressure, while Mooncake incorporates cache location into routing. Following these two ideas, I would favor adjusting resource-pool ratios and KV placement together as the load changes. Bringing state movement and phase resources into the same scheduling problem is the space that a disaggregated architecture truly opens up.[1][4]
